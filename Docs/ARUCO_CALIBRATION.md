# ArUco chassis calibration

Aligning the virtual UR3e with the real one by looking at a printed ArUco tag on the robot's
chassis, through the Quest's passthrough cameras.

This is the automatic counterpart to `MRRobotRegistrationTool`, which does the same job by having
you place three point pairs by hand. That still works and is still the fallback: it needs no tag,
no printer and no camera permission, and it works over Quest Link.

---

## The flow

Open the ROS control panel (left controller **Menu** button), press **Calibrate**, then:

| Step | What happens |
|---|---|
| Press **Find Tag** | Opens the passthrough camera and searches for up to 10 s |
| Tag found | The robot **moves onto it immediately**, and the panel asks you to agree |
| Nudge the **thumbstick** up/down | Trims the robot's height live, against the real one in front of you |
| Press **Apply** | The pose is kept and the camera closes |
| Press **Cancel** | Everything goes back exactly as it was |
| Nothing found | After 10 s the panel says *what* was missing, not just that it failed |

The result is shown by actually moving the robot rather than by drawing a ghost of it, because
the question being asked — does the virtual arm line up with the real one? — can only honestly be
answered by looking at both through the passthrough at once. Cancelling restores the previous
pose exactly, so agreeing is the only thing that commits.

A yellow square with red/green/blue axes is drawn where the calibration thinks the tag is. **Look
at it.** If it sits on the printed tag, the camera geometry is right. If it floats consistently
off to one side, see [Checking the lens offset](#checking-the-lens-offset) — that is the one part
of this pipeline nothing else can detect.

---

## This only works in the APK

Passthrough camera access is gated behind `horizonos.permission.HEADSET_CAMERA`, which exists
only on the headset. There is no passthrough camera over Quest Link and none in the Editor, so:

- In the Editor or over Link, **Find Tag** reports *"Passthrough camera access is Android-only"*
  and does nothing. That is deliberate — the alternative is a button that appears to hang for ten
  seconds.
- Testing this feature means **Build and Run** to the headset (Option B in
  `MVP_QUEST3_SETUP.md`).
- Requirements: Quest 3 or 3S on Horizon OS v74 or newer. The permission is requested at runtime
  the first time you press the button; it is declared in `Assets/Plugins/Android/AndroidManifest.xml`.

To check the maths without a headset, run **XRViz → Check ArUco Detector** (below).

## Printing the tag

Use **XRViz → Export ArUco Calibration Tag…**. It draws the marker from the same code tables the
detector reads, so the printed tag and the decoder cannot disagree about what the dictionary is.

1. Pick the **dictionary** and **marker id**. `Dict4x4_50` is the default and the right choice for
   a tag read across a room: it tolerates one wrong bit across only 50 codes. `Dict4x4_250` packs
   five times as many codes into the same 16 bits and tolerates no more error, so it is a worse
   choice, not a bigger one.
2. Set the **marker size** — the side of the black square, *not* the page. 150 mm is a sensible
   default for a UR3e chassis.
3. Print at **100 % scale**. Turn off "fit to page" / "shrink to fit"; those silently rescale the
   tag, and the size is what sets the distance to the robot.
4. **Measure the printed black square with a ruler** and put that number, in metres, into the
   calibrator's **Marker Size**. The exporter tells you what it should be, but the print is the
   ground truth, and a 2 % size error is a 2 % distance error.
5. Mount it **flat on the chassis top, printed face up, centred over the base column**, with the
   top of the print facing the way the robot faces. Keep it flat — a tag bowed over a curved
   surface reads as tilted.

Leave the white margin around the marker intact. The detector finds the tag by tracing the outside
of its black border, which it cannot do if the border runs into something else dark.

## Configuring it

On the **ArUco Calibration** object in `MVP_UR3e_MR.unity` (regenerated by
**XRViz → Create MR MVP Scene (UR3e)**):

### `ArucoRobotCalibrator`

| Field | What it means |
|---|---|
| **Dictionary** | Must match the printed tag. A mismatch decodes as nothing at all. |
| **Marker Id** | The id on the chassis. `-1` accepts any tag in the dictionary — convenient on a bench, a hazard in a room with other tags in it. |
| **Marker Size Metres** | Side of the black square as measured off the print. Scales the whole result. |
| **Vertical Mode** | `Keep Robot Height` (default) takes only horizontal position and yaw from the tag and leaves the height alone — **Tag Height Above Base is then unused and needs no measuring**. `From Tag Height` places the base below the tag by that number. |
| **Tag Height Above Base** | Only used by `From Tag Height`. Height of the tag above the robot's base frame. |
| **Height Nudge Metres Per Second** | Thumbstick trim speed while waiting to confirm. 0 disables it. |
| **Tag Planar Offset** | Horizontal offset from the base frame to the tag centre, in the robot's own frame (x right, y forward). Leave at zero if the tag really is centred on the column. |
| **Tag Yaw Offset Degrees** | Rotation from "the top of the printed tag" to "the direction the robot faces". Stays at zero if you mount the tag with its top facing the robot's front. |
| **Level To Horizontal** | Forces the placed robot upright, taking only the tag's yaw. **Leave this on.** The robot stands on a floor, and a single planar marker estimates tilt far less reliably than it estimates yaw. |
| **Apply Mode** | `Auto` moves whatever actually owns the robot's pose (below). |

### `PassthroughCameraFeed`

| Field | What it means |
|---|---|
| **Head Anchor** | `CenterEyeAnchor` under the Camera Rig. The camera pose is built out from it. |
| **Head To Camera Position / Euler** | Where the lens sits relative to the head anchor. Used only when the device will not report its own lens pose. |
| **Fallback Intrinsics** | Used only when the device will not report its own. |
| **Requested Resolution** | Leave at **1280x1280**. See below. |
| **Device Name Override** | Leave empty unless the log says the search picked the wrong camera. Takes a **Unity** device name (`Camera 1`), not a camera2 id (`50`). |

### Two camera lists, and the trap between them

The headset describes its cameras twice, and the two descriptions do not agree on names:

| | Quest 3, Horizon OS v207 |
|---|---|
| `CameraManager.getCameraIdList()` (camera2) | `1`, `50`, `51` |
| `WebCamTexture.devices` (Unity) | `Camera 0`, `Camera 1`, `Camera 2` |

Only camera2 can say *which* camera is the passthrough one — that lives in Meta's vendor
metadata (`com.meta.extra_metadata.camera_source == 0`, `position` = 0 left / 1 right), which
picks out ids `50` and `51`. But only Unity's names open anything: handing `WebCamTexture` the
id `50` logs `Cannot find webcam device 50`, returns a texture that never plays, and produces
**no frames at all** — which downstream is indistinguishable from a dark room, so the search
just times out as though the tag were missing.

What holds between the lists is the **order**: both are the same camera service enumeration,
so the nth id is the nth device. `ResolveDevice` maps across by index, and only while the two
lists are the same length — if Unity ever hides a camera camera2 reports, the indices shift and
the mapping would silently open the wrong lens, so it refuses instead.

The camera2 id is still needed *after* the camera opens: the factory calibration
(`LENS_INTRINSIC_CALIBRATION`, `LENS_POSE_TRANSLATION`/`ROTATION`) is keyed by id, not by
device name. `ReadDeviceCalibration` takes the id for that reason — pass it the Unity name and
it silently reads nothing and falls back to the serialized guess.

### The lens pose is not a lens tilt

`LENS_POSE_ROTATION` is **not** "how the lens is tilted relative to the head". It is the
rotation from the Android device frame *into the camera's own frame*, where z runs along the
optical axis and y points **down** the image. For any outward-facing camera that contains a
~180 degrees flip about x, because the camera looks along −z of a device frame whose +z faces
the wearer. The Quest 3 reports 169.2 degrees about −x: the 180 flip, less the 10.8 degrees the
passthrough camera is tilted down by.

Applying it as a head-to-camera tilt aims the camera **backwards and upside down**, 158 degrees
from where it is really looking. Detection is unaffected — that happens in image space — so the
tag is found normally and only the *placement* moves: the robot lands metres away, in the air.

The conversion, composed from inverting it, flipping image-down to Unity-up, and negating z for
the head frame, is a plain permutation:

```
(x, y, z, w)_android  ->  (w, -z, -y, -x)_unity
```

`ReadDeviceCalibration` checks the result: if the camera comes out more than 45 degrees off the
head's forward axis it logs an error and falls back to the serialized offset, because that is a
convention bug rather than a lens, and it relocates the robot rather than degrading it. The
correct answer for a Quest 3 is about **11 degrees down**, and the log says so on every run.

Measured on a Quest 3 (Horizon OS v207), camera `50`:

| | |
|---|---|
| `LENS_INTRINSIC_CALIBRATION` | `fx=fy=863.22, cx=643.67, cy=641.16` @ 1280x1280 |
| `LENS_POSE_TRANSLATION` | `(-0.0319, -0.0179, -0.0646)` → Unity `(-0.0319, -0.0179, +0.0646)` |
| `LENS_POSE_ROTATION` | 169.2° about −x → **10.8° down** in the head frame |

### Mirroring, and why it looks like the wrong dictionary

A vertical flip is a **reflection**, not a rotation. Get it wrong and the picture is not
visibly upside down — it is mirrored, and:

* contours are still traced (a square is a square either way),
* `ExtractQuad` still forces the winding clockwise, so the quad is accepted,
* and then **every tag decodes as nothing**, because `TryIdentify` searches the four rotations
  and no reflection.

The symptom is therefore *"square shapes found, none decoded"* — indistinguishable from a tag
printed from the wrong dictionary, which sends you off to reprint a tag that was fine.

`ArucoDictionary.IdentifiesWhenMirrored` exists to tell the two apart. The detector counts
quads that would have decoded had the image not been reflected, and the panel says `MIRRORED`
in the live counters, so the failure names its own cause. It is a **diagnostic only** — a
mirrored pose is wrong in a way nothing downstream could catch, so it is never accepted.

The fix is the feed's **Vertical Flip**: `Auto` trusts `WebCamTexture.videoVerticallyMirrored`;
force `Flip` or `Dont Flip` if the device misreports it. The feed logs the value it saw, the
rotation angle and which way it flipped on the first frame of every run.

#### Ids that hide the problem

Some codes are symmetric under reflection, so they decode to **their own id** in a mirrored
image. Those give a silently reflected *pose* instead of a failure — the one outcome nothing
can catch. Do not print one:

| Dictionary | Mirror-ambiguous ids |
|---|---|
| `Dict4x4_50` | **8, 9, 17, 47** |
| `Dict4x4_250` | 66 of the 250 — check before choosing |
| `Dict5x5_250` | 25, 30, 96, 102, 129, 188, 208 |
| `Dict6x6_250` | none |

**XRViz → Check ArUco Detector** prints this list, so it stays true if a dictionary is added.

### Why the requested resolution is square

The Quest 3 passthrough sensor's active array is **1280x1280**, and the intrinsics it reports
(`fx=fy=863.2, cx=643.7, cy=641.2`) are quoted against that array. Asking for 1280x1280 makes
`PinholeIntrinsics.ScaledTo` the identity, so those numbers apply verbatim.

The obvious 1280x960 does not. `ScaledTo` assumes a resize and scales `fy` by 960/1280, but a
4:3 stream off a square sensor is a vertical **crop**, which leaves `fy` alone — a 25% error in
one focal length. Nothing looks broken; the solved pose just leans, and the robot lands
confidently in the wrong place.

## Height is the axis a tag is worst at

A single planar marker pins **horizontal position and yaw** well. Height is the weakest thing it
gives, and it is also the axis that a wrong marker size, a wrong lens offset and a wrong tag
mounting height all come out along — three numbers that come from outside the code, two of them
guesses. So by default the height is not taken from the tag at all:

* **`Keep Robot Height`** leaves the robot at the height it already stands at and moves it only
  horizontally, plus yaw. Nothing about the tag's position on the chassis has to be measured.
* **Thumbstick up/down** then trims that height while the proposal is on screen, before Apply.
  Either stick, 25 cm/s, deadzoned. The panel shows the trim in centimetres as you go.

The trim moves *whatever was moved* — the robot when it owns its pose, the TF origin when TF
does. Shifting the TF origin carries the scan and the cloud with the robot, which is what is
wanted; shifting the robot alone there would be undone on the next TF update. **Cancel** still
restores the pose from before the calibration started: the trim never touches the undo state.

The tag gizmo deliberately stays where the tag was *measured*, not where the robot ended up. It
is the check on the camera geometry, so moving it with the trim would destroy the one thing it
is for. In `Keep Robot Height` a gizmo that sits below the real tag no longer means the
placement is wrong — only that the height estimate was, which is exactly what that mode ignores.

## What actually gets moved

Two different things own the robot's pose, and moving the wrong one looks like it works and then
silently snaps back a frame later. `Apply Mode: Auto` picks correctly:

- **The robot is anchored to TF** (the usual case once the ROS side is up): the calibrator moves
  the **TF origin** — the `RosTfTree` transform, which is what "where the robot's fixed frame is
  in this room" physically means. Moving the robot itself would be undone by TF on the next
  frame. This is the better outcome anyway: the laser scan and the point cloud come along, all
  still consistent with each other, which is the entire point of TF placement.
- **The robot is placed by hand**: the calibrator moves the robot through its `PlacementHandle`,
  and re-homes the grab sphere onto the new pose.

If you force `MoveRobot` while TF anchoring is on, the calibrator switches the robot to hand
placement so the result sticks, and says so in the status line. Cancelling puts that back too.

## Checking the lens offset

Everything from the image to the pose is verifiable maths, checked by the self-check below. One
number is not: **where the passthrough lens sits relative to tracking space**. An error there is a
constant error in the placed robot, and no residual or reprojection figure can reveal it.

`PassthroughCameraFeed` reads the lens pose from the Android camera characteristics
(`LENS_POSE_TRANSLATION` / `LENS_POSE_ROTATION`) when the device fills them in, and falls back to
the serialized `Head To Camera Position` otherwise. **The panel's status line says which of the
two is in use** — a line containing `SERIALIZED lens offset` means the device declined and the
offset is a guess that may need tuning.

The marker gizmo is how you tune it. Calibrate, then look at the yellow square:

- **Square sits on the real tag** → the offset is right. Apply.
- **Square is consistently displaced** in the same direction however you stand → adjust
  `Head To Camera Position` by roughly that displacement and try again.
- **Square is displaced differently depending on where you stand** → that is an intrinsics
  problem, not an offset one. Check the status line for `ASSUMED intrinsics`.

If the device never reports its lens pose and tuning by hand proves fiddly, adding Meta's
`com.meta.xr.mrutilitykit` package gives a supported `PassthroughCameraAccess` component that
provides texture, intrinsics and pose together; `PassthroughCameraFeed` is deliberately the only
place that would need changing.

## Checking the maths without a headset

**XRViz → Check ArUco Detector** renders synthetic marker images from known camera poses, runs the
whole pipeline over them, and compares the result against ground truth. It logs a PASS/FAIL line
plus the worst errors it saw.

It covers 180 viewpoints (4 ids × 5 in-plane spins × 3 tilts × 3 distances) and every id of every
supported dictionary at all four rotations. Expected results on a 1280×960 frame with a 150 mm
tag:

```
worst position error    ~3 mm
worst orientation error ~1.5 deg
worst reprojection      ~0.4 px
```

Those are on synthetic hard-edged images, which are sharper than a real camera and so pessimistic
about sub-pixel accuracy and optimistic about everything else. Run it after touching anything in
`Assets/XRViz/Scripts/Calibration/`.

## Troubleshooting

While a search is running the panel shows live counters:

```
Looking... 23 frames, 148 outlines, 2 quads, 0 tags (grey 6-243, mean 96)
```

Read them in order - each stage feeds the next, so the first one stuck at zero is the fault.
The greys are the whole frame's brightness, and they answer the question worth asking first:
**was the camera looking at anything at all?** A span of `grey 0-0` is a blank feed, and no
amount of relighting or repositioning the tag will change it.

| Symptom | Cause |
|---|---|
| *"Passthrough camera access is Android-only"* | You are in the Editor or on Quest Link. Build the APK. |
| *"Camera permission was refused"* | Grant it in the headset's app permission settings. The message names which of the two is missing. |
| *"Unity enumerated no camera devices after 3 s"* | Usually the first run after an install: the camera list is built at startup, before the permission was granted. **Close and reopen the app.** Otherwise Horizon OS older than v74. |
| *"could not be matched to any of the cameras Unity enumerated"* | The camera2 id → Unity device mapping below broke. The message prints both lists; set **Device Name Override** to the right Unity name to force it. |
| `E/Unity: Cannot find webcam device 50` in logcat | The camera2 id was passed to `WebCamTexture` as a device name. This is fixed, but it is the signature of that bug returning — see below. |
| *"nothing dark was found in any of them"* | A blank feed, not an unreadable tag - check the greys. Almost always the wrong camera being opened; the log line naming the chosen device is the place to look. |
| *"N dark outline(s) were traced but none was a convex quad"* | Tag too far, too dark, bowed, at too glancing an angle, or out of frame. Move closer and square up. |
| *"decoded only when MIRRORED"* | The camera image is reflected, not the tag's fault. Flip **Vertical Flip** on the feed — see below. |
| *"none decoded as a Dict4x4_50 tag"* | The printed tag is from a different dictionary. (If the count line shows `MIRRORED`, read the row above instead.) |
| *"saw N tag reading(s) but rejected all of them"* | Usually the wrong **Marker Id**, or a tag too small in frame. Get closer. |
| Robot lands in the right place but faces the wrong way | **Tag Yaw Offset Degrees** — try 90 / 180 / 270. |
| Robot lands at the right angle but too high or too low | **Tag Height Above Base**. |
| Robot snaps back a moment after Apply | TF is placing it and `Apply Mode` was forced to `MoveRobot`. Use `Auto`. |
| Robot floats in the air by roughly the tag's height, tag gizmo at the robot's feet | `From Tag Height` with **Tag Height Above Base still 0** — the base is placed *at* the tag. Switch Vertical Mode to `Keep Robot Height`, or measure base frame → tag surface and set it. |
| Robot lines up horizontally but sits too high or too low | Thumbstick up/down before pressing Apply. If it is out every time, the robot's own resting height is wrong, not the calibration. |
| Robot lands metres away and at the wrong angle, though the tag reads fine | The lens pose convention — see above. The log says how far off head-forward the camera came out; it should be ~11°. |
| Everything is off by a constant few centimetres | The lens offset — see above. Note `LENS_POSE_TRANSLATION` is measured from the device's own reference point, which is not necessarily the head anchor. |

## How it works

`Assets/XRViz/Scripts/Calibration/`:

- **`ArucoDictionary.cs`** — the marker code tables for the supported OpenCV dictionaries, plus
  id/rotation lookup. The tables are *data*, dumped from opencv-contrib 5.0.0 and verified entry
  by entry against what `cv2.aruco.generateImageMarker` actually draws. They are not derivable and
  must not be hand-edited.
- **`ArucoDetector.cs`** — image in, identified markers with sub-pixel corners out. Adaptive
  threshold → trace dark outlines → keep convex quads → unwarp to a canonical grid → read the
  cells → dictionary lookup over all four rotations → fit each side to the underlying grey-level
  edge and re-intersect. No OpenCV and no native plugin, so it survives the Quest APK build.
  Runs on a worker thread; a full-resolution frame is tens of milliseconds, which is a visible
  hitch if done on the main thread.
- **`MarkerPoseSolver.cs`** — four corners plus intrinsics to a 6-DoF pose. Closed-form
  homography guess, then Gauss-Newton on the reprojection error. Both solutions of the planar
  ambiguity are refined and the better one returned.
- **`PassthroughCameraFeed.cs`** — grayscale frames with intrinsics and a world pose. The camera
  pose is captured *with the pixels*, because detection finishes a frame or two later and the
  headset has moved by then.

  Two things about opening the camera are worth knowing, because both fail silently:

  - **A Quest 3 reports five cameras, not two.** On this headset the list is ids
    `1, 50, 51, 60, 70`, and the passthrough pair is `50` (left) and `51` (right) - *not* at the
    front. Indexing the device list by eye opens camera `1`, which plays perfectly happily and
    returns solid black forever. The passthrough cameras are found by asking each camera for
    Meta's `com.meta.extra_metadata.camera_source` and `.position` vendor metadata instead of
    assuming an order, and the chosen device is logged every time. `Device Name Override` on the
    component forces a specific one if that ever picks wrong.
  - **The device list is empty for a few frames after the permission is granted.** Unity
    enumerates the cameras at startup, before the user has answered the dialog. Opening retries
    for three seconds rather than failing on the first empty list; if it still comes back empty,
    the app has to be restarted, and the message says so.

  `adb shell "dumpsys media.camera | head -30"` lists the headset's cameras and logs which
  package connected to which - the fastest way to tell a wrong-camera bug from a tag one.
- **`ArucoRobotCalibrator.cs`** — the state machine above, the tag-to-base geometry, and the
  decision about what to move.
- **`MarkerPoseGizmo.cs`** — the square drawn where the tag is believed to be.

### Conventions worth knowing before editing

- The detector reports corners with **pixel centres at +0.5**, matching what `cx`/`cy` mean.
  Working in array-index space instead is a half-pixel bias on every corner and a systematic lean
  on every pose.
- `GetPixels32` hands back the **bottom row first**; every camera model measures rows from the
  top. `PassthroughCameraFeed` flips during the grayscale conversion so that one convention holds
  from there on. Getting this wrong mirrors every pose, which looks almost right.
- `MarkerPose.Rotation` gives `forward` = out of the printed face and `up` = towards the top of
  the print. Its **`right` is mirrored** (it points to the printed *left*): the OpenCV-to-Unity Y
  flip is a reflection, so one axis has to give. Nothing reads `right`; anything added that does
  must know.
